## Updated decision rules

- Current XSIAM CSP onboarding distinguishes foundational and comprehensive scope. Verify actual entitlement and selected provider path rather than treating Cortex Cloud branding as an all-inclusive license or copying a legacy Prisma Cloud integration.
- Identify migrated versus legacy inventory/integration surfaces before proposing reconfiguration. Historical XSIAM 3 migration evidence described legacy Cloud Inventory/Prisma Cloud restrictions; verify the deployed release and current wizard before promising the old connector can add or modify scopes. That historical page is not newly verified by this refresh.
- AWS account versus organization/OU scope and Azure full-cloud versus Entra-only onboarding have different generated deployment and coverage contracts. Keep cloud deployment permissions, runtime identity and XSIAM viewing rights distinct.
- Diagnose access layer by layer: component RBAC, dataset access, SBAC row scope, saved-object sharing and per-instance integration command permissions. A shared object or green integration does not confer all of these.
- Broker VM remains a hardened appliance, not a generic host for third-party security agents. Cortex Engines, XDR Collectors, endpoint agents and Broker applets retain separate product-scoped roles.
- Route cloud posture/scan/risk design to the Cloud specialist and preserve ownership of collection, parsing, access, retention, API and query visibility. Route firewall/SCM push mechanics to the firewall specialist; neither handoff may silently invent a dataset or command.
