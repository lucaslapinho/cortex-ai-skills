# Official Cortex Documentation Source Register

Review date: 2026-09-04  
Scope: current official Palo Alto Networks documentation, official Palo Alto Networks developer documentation, and official Palo Alto Networks GitHub repositories only.

## Purpose and evidence policy

This register is the authoritative-source baseline for the modular Cortex AI Skills ecosystem. It is a research index, not proof that a specific tenant exposes a feature, dataset, field, command, license, API permission, or UI control.

Source precedence within this register:

1. Current product documentation and current release notes.
2. Current platform API and command references.
3. Current developer documentation.
4. Official living repositories and examples, with a pinned revision required for reproducibility.
5. Explicitly identified legacy or version-specific documentation, retained only for compatibility analysis.

Evidence classifications:

| Evidence classification | Meaning |
|---|---|
| CURRENT-OFFICIAL | Current first-party documentation for the named product surface. |
| CURRENT-OFFICIAL; TENANT-DEPENDENT | Current behavior, but available objects, schema, data, or results depend on tenant configuration and ingestion. |
| CURRENT-OFFICIAL; LICENSE-DEPENDENT | Current behavior whose availability depends on edition, add-on, or entitlement. |
| CURRENT-OFFICIAL; VERSION-DEPENDENT | First-party documentation tied to a named product or release line; verify the deployed version. |
| CURRENT-OFFICIAL; ROLLOUT-DEPENDENT | Current release-note behavior that can depend on tenant rollout or upgrade state. |
| OFFICIAL-LIVING-REPOSITORY; VERSION-PIN-REQUIRED | Official code/examples that change over time; pin a tag, commit, and tool version before reuse. |
| LEGACY-COMPATIBLE; DEPRECATED-DOCUMENTATION | Legacy surface still referenced for compatibility, but its documentation is deprecated or unmaintained. Prefer its documented successor where one exists. |
| DEPRECATED; SUCCESSOR-DOCUMENTED | Palo Alto Networks explicitly identifies the surface as deprecated and documents a replacement. |

These labels describe source provenance and applicability. Skill outputs must map them to the canonical claim classes plus validation qualifiers defined by the architecture:

| Source-register label | Canonical status and qualifiers |
|---|---|
| `CURRENT-OFFICIAL` | `VERIFIED / OFFICIAL-CURRENT` for the documented claim. |
| `CURRENT-OFFICIAL; TENANT-DEPENDENT` | `VERIFIED / OFFICIAL-CURRENT` for general behavior; tenant-specific availability or result is `UNVERIFIED / TENANT-UNVERIFIED`. |
| `CURRENT-OFFICIAL; LICENSE-DEPENDENT` | `VERSION-DEPENDENT / OFFICIAL-CURRENT / TENANT-UNVERIFIED` until the target tenant entitlement is checked; the note must identify licensing as the unresolved condition. |
| `CURRENT-OFFICIAL; VERSION-DEPENDENT` | `VERSION-DEPENDENT / OFFICIAL-CURRENT`, naming the applicable release line. |
| `CURRENT-OFFICIAL; ROLLOUT-DEPENDENT` | `VERSION-DEPENDENT / OFFICIAL-CURRENT / TENANT-UNVERIFIED`. |
| `OFFICIAL-LIVING-REPOSITORY; VERSION-PIN-REQUIRED` | `VERIFIED / OFFICIAL-EXAMPLE` only for the reviewed revision; otherwise `VERSION-DEPENDENT`. |
| `LEGACY-COMPATIBLE; DEPRECATED-DOCUMENTATION` | Split the claims: endpoint compatibility is `VERSION-DEPENDENT / OFFICIAL-CURRENT / TENANT-UNVERIFIED`; the retired documentation lifecycle is `DEPRECATED / OFFICIAL-CURRENT`. Never attach two canonical statuses to one claim. |
| `DEPRECATED; SUCCESSOR-DOCUMENTED` | `DEPRECATED / OFFICIAL-CURRENT`. |

The Access/review date records this research review, not the publication date of the linked page. All numerical limits and licensing statements must be rechecked before production deployment.

## High-impact cautions and discrepancies

1. XSIAM 3 terminology and compatibility identifiers coexist. Current user-facing concepts are Case and Issue, but legacy Incident and Alert labels remain in some APIs, paths, commands, datasets, fields, and playbook context keys. A skill must translate the concept while preserving literal identifiers required by the platform.
2. Insert Parsed Alerts is a legacy compatibility surface. Current XSIAM administration material still refers to pre-parsed alert ingestion, while current API release notes classify the endpoint as legacy without an identified successor and state that older XSIAM API documentation is deprecated and unmaintained. New integrations need an explicit compatibility and migration decision.
3. Cortex Cloud February 2026 release notes describe Data Sources/Integrations and RBAC/SBAC changes only for Cortex Cloud. They are not XSIAM release evidence. Use the product-specific XSIAM permission pages for XSIAM and verify effective tenant access; keep overlapping labels separated across products.
4. The deprecated PAN-OS External Dynamic List integration must not be proposed for new designs. Use the documented EDL or Generic Export Indicators service.
5. XQL success in Query Center does not prove correlation-rule compatibility. Correlation types impose separate stage, filter, action, timeframe, schedule, and safeguard constraints.
6. Private sub-playbook context is not a security boundary. RBAC, SBAC, integration-instance permissions, and Case/Issue permissions determine authorization.
7. Dataset, field, entity, and Finding documentation describes supported schemas, not tenant population. Every production query requires tenant discovery and representative execution evidence.
8. Official GitHub repositories are living sources. A reusable Skill must pin a commit or release and record the demisto-sdk version used to format, validate, test, and prepare content.
9. Official `regextract()` references disagree on return shape. The current general command reference documents a scalar string containing the first capture group, while the XDR 3.x reference documents an array/list of matches and RE2 behavior. Treat this as product/version dependent, select one documented target explicitly, and validate downstream type assumptions in the tenant compiler before presenting the query as tenant-compatible.
10. XQL is not inherently read-only. The documented `target` stage persists results and defaults to overwrite when `append` is omitted; production use requires explicit state-change authorization and recovery controls.
